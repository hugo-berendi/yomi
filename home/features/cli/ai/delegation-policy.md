## Efficient delegation on Inari

Keep the user's current main model. Use cheaper subagents for genuinely separate, bounded tasks: finding relevant files, short documentation lookups, log triage, mechanical changes with a clear acceptance check, and targeted tests. Do a trivial one-step task or dependent sequence yourself; spawning extra agents is not automatically cheaper.

- Codex: use the fast_task role or GPT-6 Luna at low reasoning for routine delegated work. The configured subagent default is gpt-6-luna. Do difficult diagnosis, architecture, security decisions and final review in the parent; explicitly choose a stronger model only for a substantial independent task.
- Claude Code: use fast-task (Haiku) for routine work and quick-review (Sonnet) for a bounded review needing more reasoning. Do not send complex planning to Haiku. These workers explicitly select claude-haiku-5-5 and claude-sonnet-5-5 on the direct Claude provider.
- OpenCode: use the named fast-task or quick-review subagent only when its configured Copilot model is present in the authenticated model catalog. Do not silently substitute an expensive model if it is unavailable.
- Local model (all three harnesses): `local-task "<task>"` runs a bounded task through OpenCode's local-task agent on Qwen3.6-35B-A3B, served by llama.cpp on this CPU. It costs no subscription usage but is slow: about two minutes to read its 12k-token prompt, then roughly 15 tokens per second, so a small fix takes three to five minutes. Use it for simple, self-contained work where that wait is fine: summarising a file or log, a targeted grep-and-report, a mechanical edit with a clear check. It may edit files in the current directory and run shell commands. Pushes, sudo, `rm -rf` and switches are rejected. Run it from the project directory with a timeout of at least 15 minutes, in the background where the harness supports it. Give it everything it needs in the prompt and review its diff before relying on it. Its answer is printed on stdout. It handles one task at a time, so do not start a second one in parallel.
- Give each child a small scope, relevant paths, constraints and an observable completion check. Send only necessary context. Start with one worker; use a second only for independent work that justifies its extra usage. Avoid nested delegation and duplicate investigations.
- Ask for compact results with evidence, changed paths and unresolved issues. The parent checks important claims and edits, and runs the required final validation. Preserve all existing permissions and approval requirements. Never expose credentials or delegate privilege changes merely to get around a restriction.
